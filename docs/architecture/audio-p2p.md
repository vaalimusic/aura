# Audio P2P · реализация этапа II

Документ описывает прямой QUIC-транспорт и его испытания. Дополнительно реализованы постоянный Aura ID и relay v2 через VPS: см. [Aura Node](../../deploy/README.md). Упоминания отсутствующего relay ниже относятся к состоянию этапа II до этого расширения.

`aura-audio` не зависит от UI/сети. Capture и playback выполняются на MTA-потоках. Проверяются PID, имя и время создания процесса. Источники — аудиосессии устройств вывода, без системного PID 0 и собственного процесса. Одноимённые дочерние процессы группируются в дерево приложения.

Process Loopback активируется штатным API Windows. Ожидание активации ограничено 5 секундами, UI не блокируется. Параметры активации удерживает COM callback. Для SILENT-кадров null-буфер не разыменовывается. Каждый GetBuffer парен с ReleaseBuffer до кодирования; COM освобождается после интерфейсов на том же потоке.

`engine.rs` управляет временем жизни. Остановка выставляет atomic flag и будит сетевой actor; network endpoint закрывается, затем завершаются audio workers. Нормальный цикл проверяет stop примерно каждые 20 мс, если API ОС возвращает управление; незавершённая активация ждёт своего таймаута. Новая сессия ожидает завершения предыдущей. События имеют поколение; старые результаты игнорируются. Ready после команды остановки не возвращает приглашение в UI.

## Протокол v1

`aura://v1/<base64url(json)>`: SocketAddr, DER-сертификат эфира, случайный токен 32 байта. Ограничены длина ссылки, размер сертификата и поля JSON. Это временная bearer capability, не публичный профиль. Секреты живут в памяти, в логах не выводятся; clipboard меняется только кнопкой копирования.

QUIC/TLS 1.3 использует quinn/rustls. Сертификат эфемерный, имя `aura.local`. Клиент создаёт изолированный trust store из сертификата приглашения; отключения TLS-проверки нет. Сервер ждёт один bidirectional control stream: `AUR1` + токен. Сравнение токена — constant-time. Ответ `OK01` разрешает медиадатаграммы. До авторизации звук не передаётся.

Datagram: `AUR1` (4 байта) + sequence u64 big endian (8) + Opus (1–1100). Принимаются только 20-мс stereo 48-kHz кадры (960 сэмплов на канал). QUIC защищает транспорт от подмены/replay; sequence нужен для аудиопорядка и диагностики. Самодельной криптографии нет.

Ограничения: 4 одновременно подключающихся/подключённых слушателя; 30 попыток в минуту; 5 секунд на авторизацию; ограниченные QUIC stream windows и datagram buffers. Очередь capture→network — 8 кадров; network→playback — 16. Медленный слушатель не блокирует захват. Следующий эфир создаёт новые ключ/токен. Индивидуального отзыва слушателя пока нет: отзыв завершает эфир целиком.

Авторизация доказывает владение приглашением. Постоянная Ed25519-идентичность и политика доверенных друзей остаются этапу III.

## Jitter и измерения

Темп задаёт WASAPI clock, а не сетевые события. Стартовая предбуферизация — 3 кадра/60 мс. После пропусков целевая предбуферизация повышается до 10 кадров, после стабильного участка постепенно снижается. Жёсткий предел очереди — 25 кадров/500 мс; переполнение отбрасывает старое аудио. Пропуски закрываются Opus PLC; при пустой очереди — тишина и предбуферизация заново. Громкость обновляется атомарно на выводе.

UI показывает RTT, jitter-очередь и диагностические пропуски. Это не измеренная задержка capture→speaker. Коррекция долгосрочного clock drift пока отсутствует: ограниченные очереди предотвращают неограниченный рост задержки, но периодические коррекции/underruns на разных clocks ещё требуют испытаний.

## Верификация и границы

Автотесты: Opus/PLC, reordering/duplicates/jitter bounds, размеры пакетов, QUIC loopback с реальным кодеком, отклонение неправильных сертификата/токена и отзыв доступа. Аппаратный `--audio-smoke`: отдельный синтетический процесс → Process Loopback → Opus → QUIC/TLS → jitter → muted WASAPI output. Пользовательские приложения не захватываются, аудио не сохраняется.

Прямое соединение по доступному IP/UDP-порту реализовано. NAT traversal, relay и discovery ещё нет. Для Интернета требуется достижимый порт.

### Ручные испытания · 2026-10-21

Пользователь подтвердил воспроизведение музыки между двумя ПК в одной LAN, затем между разными сетями. Во втором тесте вещатель находился за роутером с ручным пробросом UDP 45070 на локальный ПК. Приглашение содержало внешний адрес вещателя; слушающий ПК был подключён через мобильный интернет. Музыка на приёмнике воспроизводилась.

Базовый сценарий этапа II — разрешённая передача аудио между двумя ПК в разных сетях по доступному прямому маршруту — подтверждён пользовательским тестом. Это не подтверждает автоматический обход NAT или relay: они в тесте не использовались. Длительность сеанса, end-to-end задержка, потери и расход ресурсов отдельно не измерялись; длительное прослушивание, обрывы и смена сети ещё требуют проверки.
