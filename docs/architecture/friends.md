# Saved friends and presence

`aura-social` owns a versioned local profile: owner PeerId, display name and contact relations. Atomic same-directory replacement preserves the previous file on write errors. Validation bounds the file to 256 KiB, contacts to 128 and pending incoming requests to 32. A profile belongs to one identity; corruption or owner mismatch is reported rather than resetting consent. The desktop holds an exclusive profile lock.

Relations are Outgoing, Incoming, Accepted, Declined and Blocked. Incoming requests require explicit approval; two outgoing requests express mutual approval. Unknown Approved messages create Incoming entries, never Accepted ones. Removal stores a Blocked tombstone; network replay cannot undo it. Explicit local Add can reestablish contact.

`aura-mesh::social` owns the long-lived stable-identity swarm. Each client reserves a Circuit Relay endpoint and polls known contacts over `/aura/social/1`. Noise authenticates the sender PeerId; JSON does not contain a self-asserted identity. Messages carry a bounded name, intent and optional current relay invitation. Only locally Accepted contacts receive an invitation. A received invitation is usable only when both sides report approval. Read/write deadlines, job limits and per-peer request limits bound resource use. Relay reconnection never starts audio capture.

The desktop's audio swarm uses a fresh identity for each session. The stable social channel supplies the corresponding audio invitation, binding its ephemeral PeerId and capability to the known friend. This avoids two swarms replacing the same relay reservation. Manual bearer invitations remain supported. Profile files never store invitations, capabilities or presence.

«Слушать» performs a fresh request; cached status is only a display hint. The result carries the desktop session generation. Stop or source change invalidates a pending request, so a late response cannot start playback. CaptureReady publishes the invitation; Stop/Ended clears it. Removing any contact during a broadcast stops that broadcast, revoking already issued bearer capabilities for all listeners. Individual live listener revocation is not implemented.

Presence normally polls every four seconds and expires after thirteen seconds, observed on the next update. Snapshots are emitted only on change. Offline recipients receive queued local requests on a later poll after reconnecting; the relay does not store social messages. The pilot's 16-circuit limit constrains group size; large lists have not been load-tested. Discovery is by known Aura ID on a common configured relay, without a public catalog or DHT records.

Tests cover persistence, consent transitions, replay after blocking and invitation filtering. A local relay lifecycle test covers request/accept/live lookup/stop/offline/reconnect/removal. `--mesh-smoke` repeats the lifecycle on the configured relay using temporary identities, then captures only a synthetic child process, sends Opus using the resolved friend invitation and verifies nonzero decoded audio with muted WASAPI output.

Smart Feed stores pinned, excluded and manually ordered peer IDs in the bounded, atomically replaced `smart-feed.txt` profile file (`p`, `e`, `o` tab-separated entries). Existing files without order entries retain their previous behavior. Accepted contacts follow the saved order; new contacts are appended. Selection rotates after the current peer, skips unavailable, excluded and already attempted broadcasts, and prefers an available pinned peer. Editing uses a separate stable-ID snapshot so renames, presence changes and incoming contacts do not reorder the draft. Save removes contacts no longer accepted and appends newly accepted ones; Cancel changes nothing. Save failures keep the editor open and preserve the previous applied order. Saving refreshes invitation prefetch without stopping the current audio; a transition already in progress is allowed to finish.
